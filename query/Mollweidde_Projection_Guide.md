## Mollweide Projection Overview

**EPSG/ESRI Code**: ESRI:54009
**Type**: Pseudocylindrical equal-area projection
**Use Case**: Global thematic maps, maintaining area relationships

### Key Properties:
- **Equal-area**: Preserves area relationships (1 cm² = same area anywhere on map)
- **Central meridian**: 0° (Greenwich)
- **Projection center**: (0°N, 0°E)
- **Shape distortion**: Increases toward edges, especially at high latitudes
- **Suitable for**: Global scientific data, climate maps, population density

### Mathematical Form:
The Mollweide projection uses an elliptical boundary where:
- **Width**: 2π × R (where R = Earth radius)
- **Height**: π × R
- **Aspect ratio**: 2:1 (ellipse)

## Proj4 Definition String

```
+proj=moll +lon_0=0 +x_0=0 +y_0=0 +datum=WGS84 +units=m +no_defs +type=crs
```

### Parameter Breakdown:

| Parameter | Value | Meaning |
|-----------|-------|---------|
| `+proj=moll` | moll | Mollweide projection algorithm |
| `+lon_0=0` | 0° | Central meridian (longitude of center) |
| `+x_0=0` | 0 meters | False easting (x-offset from center) |
| `+y_0=0` | 0 meters | False northing (y-offset from center) |
| `+datum=WGS84` | WGS84 | World Geodetic System 1984 ellipsoid |
| `+units=m` | meters | Linear units for coordinates |
| `+no_defs` | - | Don't use default parameters |
| `+type=crs` | crs | Coordinate reference system type |

### Why These Values?
- **lon_0=0**: Centers the map on the Greenwich meridian (standard for world maps)
- **x_0=0, y_0=0**: No offset; (0,0) is at the projection center (0°N, 0°E)
- **WGS84**: Modern standard datum matching ETOPO 2022 source data
- **meters**: Provides precise measurements for scientific data

## Coordinate System Bounds

### Mollweide Extents (in meters):

```javascript
X: -18,040,095.70 to +18,040,095.70 meters (width: ~36.08 million meters)
Y: -9,020,047.85 to +9,020,047.85 meters (height: ~18.04 million meters)
```

### Calculation Basis:

For WGS84 ellipsoid:
- **Earth radius (R)**: ~6,371,000 meters
- **Mollweide width**: 2π × R = 2 × 3.14159 × 6,371,000 ≈ 40,030,174 meters
- **Mollweide height**: π × R = 3.14159 × 6,371,000 ≈ 20,015,087 meters

However, our actual bounds are slightly smaller:
- **Width**: 36,080,191.4 meters (≈ 2π × 5,743,365 meters)
- **Height**: 18,040,095.7 meters (≈ π × 5,743,365 meters)

This is because:
1. The reprojection from WGS84 uses a slightly different radius calculation
2. The actual data extent may not reach the theoretical maximum
3. GDAL's gdalwarp computed these bounds based on the actual transformed data

### Bounds in Leaflet:

```javascript
bounds: L.bounds(
  [[-18040095.70, -9020047.85],  // Bottom-left (xmin, ymin)
   [18040095.70, 9020047.85]]    // Top-right (xmax, ymax)
)
```

**Important**: Leaflet uses `[x, y]` order, not `[lat, lon]` for projected coordinates.

## Tile Pyramid Resolutions

### Resolution Concept:
**Resolution** = meters per pixel at a given zoom level

### Our Resolutions (zoom 0-5):

| Zoom | Resolution (m/px) | Calculation | Map Width (pixels) | Map Height (pixels) |
|------|-------------------|-------------|-------------------|---------------------|
| 0 | 140,937.5 | Base resolution | 256 | 128 |
| 1 | 70,468.75 | 140937.5 / 2 | 512 | 256 |
| 2 | 35,234.375 | 70468.75 / 2 | 1,024 | 512 |
| 3 | 17,617.1875 | 35234.375 / 2 | 2,048 | 1,024 |
| 4 | 8,808.59375 | 17617.1875 / 2 | 4,096 | 2,048 |
| 5 | 4,404.296875 | 8808.59375 / 2 | 8,192 | 4,096 |

### How Resolutions Are Calculated:

**Base Resolution (Zoom 0)**:
```
Resolution = Total_Width_meters / Total_Width_pixels
Resolution = 36,080,191.4 / 256 = 140,937.5 m/px
```

At zoom 0, the entire world fits in a 256×128 pixel tile.

**Subsequent Levels**:
Each zoom level doubles the pixel dimensions:
```
Resolution(z) = Resolution(z-1) / 2
```

### Why These Values Matter:

1. **Controls detail level**: Higher resolution = more detail visible
2. **Tile coverage**: Determines how many tiles cover the map at each zoom
3. **Data alignment**: Must match how tiles were generated by gdal2tiles

## GDAL Tile Generation Parameters

### Command Used:
```bash
gdal2tiles.py -p raster -z 0-5 -r bilinear ETOPO_final.vrt tiles_mollweide
```

### Parameter Breakdown:

#### `-p raster` (Profile: Raster)
**Purpose**: Generate tiles for custom projections

**What it does**:
- Uses the **native projection** from the source data (our Mollweide GeoTIFF)
- Creates tiles in **image pyramid** structure without reprojecting
- Suitable for use with **proj4leaflet** custom CRS definitions

**Alternatives**:
- `-p mercator`: Reprojects to Web Mercator (EPSG:3857) - wrong for our case
- `-p geodetic`: Reprojects to WGS84 plate carrée (EPSG:4326) - wrong for our case

**Why raster?**
We want to preserve the Mollweide projection in the tiles, not convert to a standard web projection.

#### `-z 0-5` (Zoom Levels)
**Purpose**: Generate tiles from zoom 0 (most zoomed out) to zoom 5 (most zoomed in)

**Tile counts per zoom**:
```
Zoom 0: 2 tiles (1 across × 2 down) - but only 1 has data
Zoom 1: 8 tiles (2×4) - partial coverage
Zoom 2: 32 tiles (4×8)
Zoom 3: 128 tiles (8×16)
Zoom 4: 512 tiles (16×32)
Zoom 5: 2,048 tiles (32×64)
Total: ~387 tiles (many outside Mollweide ellipse are empty/skipped)
```

**Why 0-5?**
- Balances detail vs. file size
- Matches our source data resolution (60 arc-seconds, ~2km)
- Zoom 5 provides ~4.4 km/pixel resolution
- Higher zooms would not add meaningful detail from source data

#### `-r bilinear` (Resampling Method)
**Purpose**: Interpolation method for creating tiles at different resolutions

**What it does**:
- Uses **bilinear interpolation** to smooth values between pixels
- Each output pixel is weighted average of 4 nearest input pixels

**Alternatives**:
- `near` (nearest neighbor): Fast, preserves exact values, blocky appearance
- `cubic`: Smoother, slower, can introduce slight artifacts
- `lanczos`: Highest quality, slowest, best for photos

**Why bilinear?**
- Good balance of speed and quality for elevation/bathymetry data
- Produces smooth color gradients
- Doesn't create extreme values (cubic/lanczos can overshoot)
- Faster than cubic/lanczos

#### Source: `ETOPO_final.vrt`
**Type**: Virtual Raster (VRT file)

**What it contains**:
```xml
<VRTDataset rasterXSize="48299" rasterYSize="24150">
  <VRTRasterBand band="1"> <!-- Red -->
    <SourceFilename>ETOPO_final_R.tif</SourceFilename>
  </VRTRasterBand>
  <VRTRasterBand band="2"> <!-- Green -->
    <SourceFilename>ETOPO_final_G.tif</SourceFilename>
  </VRTRasterBand>
  <VRTRasterBand band="3"> <!-- Blue -->
    <SourceFilename>ETOPO_final_B.tif</SourceFilename>
  </VRTRasterBand>
</VRTDataset>
```

**Why VRT?**
- Combines 3 separate single-band GeoTIFFs into RGB without copying data
- Memory-efficient (references source files, doesn't duplicate)
- Fast to create and modify

#### Output: `tiles_mollweide/`
**Structure**:
```
tiles_mollweide/
├── 0/
│   └── 0/
│       └── 0.png
├── 1/
│   ├── 0/
│   │   ├── 0.png
│   │   └── 1.png
│   └── 1/
│       ├── 0.png
│       └── 1.png
├── 2/
│   └── ... (more tiles)
...
└── 5/
    └── ... (many tiles)
```

**Naming convention**: `{z}/{x}/{y}.png`
- `z`: Zoom level (0-5)
- `x`: Tile column (increases eastward)
- `y`: Tile row (increases southward, top-down)

## Leaflet CRS Configuration

### Origin Parameter

```javascript
origin: [-18040095.70, 9020047.85]  // [x, y] in meters
```

**What it represents**: Top-left corner of the tile grid in Mollweide coordinates

**Why this value?**
- Leaflet's tile coordinate system starts at `(0, 0)` in the **top-left**
- Our Mollweide bounds: `x: [-18040095.70, +18040095.70]`, `y: [-9020047.85, +9020047.85]`
- Top-left corner: `x = xmin = -18040095.70`, `y = ymax = +9020047.85`

**Tile (0,0) at zoom 0** corresponds to this map coordinate.

### Resolutions Array

```javascript
resolutions: [
  140937.5,      // Zoom 0
  70468.75,      // Zoom 1
  35234.375,     // Zoom 2
  17617.1875,    // Zoom 3
  8808.59375,    // Zoom 4
  4404.296875    // Zoom 5
]
```

**Purpose**: Tells Leaflet the map scale at each zoom level

**How Leaflet uses this**:
1. User pans/zooms to a coordinate `[lat, lon]`
2. Proj4 converts `[lat, lon]` → `[x_meters, y_meters]` in Mollweide
3. Leaflet calculates: `pixel_x = (x_meters - origin_x) / resolution(z)`
4. Leaflet calculates: `pixel_y = (origin_y - y_meters) / resolution(z)` (note: y is flipped)
5. Tile coordinates: `tile_x = floor(pixel_x / 256)`, `tile_y = floor(pixel_y / 256)`
6. Leaflet loads: `tiles_mollweide/{z}/{tile_x}/{tile_y}.png`

### Bounds Parameter

```javascript
bounds: L.bounds(
  [[-18040095.70, -9020047.85],  // [xmin, ymin]
   [18040095.70, 9020047.85]]    // [xmax, ymax]
)
```

**Purpose**: Restricts map panning to valid coordinate range

**What happens**:
- User cannot pan beyond these bounds
- Coordinates outside are clipped
- Prevents requesting tiles that don't exist

## Tile Addressing Scheme

### XYZ Tile Grid

**Standard web tile grid** (used by Google Maps, OpenStreetMap, etc.):
- Origin at **top-left** of the world
- `x` increases **eastward** (left to right)
- `y` increases **southward** (top to bottom)
- Each zoom level doubles the tiles in each direction

### Mollweide Tile Coverage

At zoom 0:
```
Tile (0,0): Top-left quadrant of Mollweide ellipse
Tile (0,1): Bottom-left quadrant
```

Many tiles at the edges are **empty** because:
- Mollweide projects to an **ellipse**, not a rectangle
- Tiles outside the ellipse contain no valid data
- gdal2tiles skips generating empty tiles (saves space)

### Tile Size

**256×256 pixels** (standard)

**Why 256?**
- Web standard (originated with Google Maps)
- Good balance: not too large (slow download), not too small (too many requests)
- Hardware-friendly (powers of 2)

## Data Pipeline Summary

### 1. Source Data
- **Input**: ETOPO_2022_v1_60s_N90W180_bed.tif (WGS84, ~2km resolution)
- **Format**: Float32 GeoTIFF (elevation values in meters)

### 2. Reprojection
```bash
gdalwarp -s_srs EPSG:4326 -t_srs ESRI:54009 -r bilinear \
  -co TILED=YES -co BIGTIFF=YES \
  ETOPO_2022_v1_60s_N90W180_bed.tif \
  ETOPO_2022_bedrock_clean.tif
```
- **Output size**: 48,299 × 24,150 pixels
- **Projection**: Mollweide (ESRI:54009)
- **Resolution**: ~747 meters/pixel

### 3. Color Relief
```bash
gdaldem color-relief ETOPO_2022_bedrock_clean.tif \
  etopo_colors_updated.txt \
  ETOPO_2022_bedrock_colored.tif
```
- **Output**: RGB GeoTIFF (3 bands, Byte type)
- **Colors**: Blue (ocean) → Green/Tan (land) → Dark Brown (mountains)

### 4. Ice Overlay
```bash
gdal_calc.py --calc "where(logical_and(I>=100, I<=5000), 255, A)" \
  -A ETOPO_2022_bedrock_colored.tif --A_band 1 \
  -I ETOPO_2022_ice_thickness_clean.tif \
  --outfile ETOPO_final_R.tif
# (repeat for G and B bands)
```
- **Logic**: If ice thickness > 100m, set pixel to 255 (white)
- **Output**: 3 separate single-band GeoTIFFs (R, G, B)

### 5. VRT Assembly
```bash
gdalbuildvrt -separate ETOPO_final.vrt \
  ETOPO_final_R.tif ETOPO_final_G.tif ETOPO_final_B.tif
```
- **Output**: Virtual RGB raster (references 3 TIFFs)

### 6. Tile Generation
```bash
gdal2tiles.py -p raster -z 0-5 -r bilinear \
  ETOPO_final.vrt tiles_mollweide
```
- **Output**: 387 PNG tiles (19MB)
- **Structure**: `{z}/{x}/{y}.png`

## Best Practices & Notes

### Projection Choice
- **Mollweide**: Good for equal-area global maps
- **Alternatives**:
  - Web Mercator (EPSG:3857): Standard web maps, preserves shape near equator
  - Plate Carrée (EPSG:4326): Simple, but distorts area significantly
  - Robinson, Winkel Tripel: Compromise projections for aesthetics

### Tile Generation Tips
1. **Use VRT when possible**: Avoids data duplication
2. **Match zoom levels to data resolution**: Don't over-zoom
3. **Raster profile for custom projections**: Required for proj4leaflet
4. **Bilinear resampling**: Good default for continuous data (elevation, temperature)
5. **Nearest neighbor for categorical**: Use for land cover, classification maps

### Performance Optimization
- **Tile size**: 256×256 is standard; 512×512 reduces requests but larger files
- **Compression**: PNG compression is automatic (lossless)
- **Caching**: Use HTTP caching headers (handled by nginx in Docker setup)
- **CDN**: For production, serve tiles from CDN for global performance

### Common Issues
1. **Tiles appear in wrong location**: Check origin and bounds
2. **Map doesn't pan correctly**: Verify resolution array
3. **Tiles missing**: Check zoom level range matches generation
4. **Colors wrong**: Verify color relief file and band order (RGB)
